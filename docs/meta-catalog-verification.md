# التحقق من إصلاح Meta Pixel والكتالوج

## صور صفحة المنتج ومعاينة التعديل — 24 أكتوبر 2026

- الفحص شمل 221 منتجًا. طرق تحميل الصور كانت مختلفة: بطاقات المتجر تعرض المصدر المباشر، وصفحة المنتج تضيف رقم إصدار للمصدر الخارجي، ومحرر الإدارة يستخدم Next Image optimizer. فشلت 14 معاينة من أصل 449 رابطًا مختلفًا في مسار المحرر القديم، منها رفض HTTP 403 من مصادر خارجية وHTTP 400 لروابط HTTP. وفشلت 18 محاولة من 901 طلب للمصادر المباشرة ونسخها المرقمة. نجاح ملف الكتالوج وحده لم يكن يثبت نجاح الصور داخل الصفحة أو المحرر.
- الصفحة ومعاينة الصور المحفوظة في المحرر تستخدمان الآن مسار JPEG المحلي `/api/catalog/image/` نفسه. تُعرض الاستبدالات غير المحفوظة من مصدرها الجديد، مع الحفاظ على ربط معاينة كل صورة بموقعها الأصلي عند إعادة ترتيب المعرض. اختيار الصورة مرتبط بمعرّف المنتج حتى لا تبقى صورة منتج سابق بعد التنقل.
- أُجري فحص فعلي لكل الروابط التي تُنتجها دالة العرض الجديدة: **452/452 رابطًا نجحت** للـ221 منتجًا، بينها الصور الرئيسية وصور المعرض. كل استجابة فُكّت بواسطة sharp، وفُحصت أبعادها وتباين البكسلات لاستبعاد الصور الفارغة. عدد بصمات الملفات المختلفة 414؛ هذا الفحص يثبت إمكانية تحميل صور غير فارغة، ولا يثبت أن كل زاوية تصوير مختلفة أو أن Meta استوردها.
- كانت 76 قائمة صور محفوظة بالصيغة القديمة المفصولة بفواصل لا تدخل كتالوج Meta. الباك إند يستخدم الآن محللًا مشتركًا لقوائم JSON والقوائم القديمة؛ توليد الملف المعدل من بيانات المنتجات المنشورة أعطى 221 صورة رئيسية و231 صورة معرض بدلًا من 140 صورة معرض. معرفات المنتجات باقية كما هي.
- كاش JPEG أصبح مربوطًا بمصادر صور المنتج حتى لا يعيد الصورة القديمة بعد استبدالها. تُنقل ملفات الكاش القديمة عندما تكون أحدث من آخر تعديل للمنتج؛ فحص رؤوس ملفات الكاش المنشورة أثبت توافق **452/452** مع شرط النقل. تغييرات الوصف أو السعر لا تغيّر مفتاح مصدر الصورة بعد النقل. روابط صور الملف تحمل رقم إصدار، ومسار الصور في الواجهة يمرّره للباك إند ويحترم مدة الكاش الواردة منه.
- صورة مشاركة صفحة المنتج وبيانات SEO تستخدم المسار المحلي أيضًا، مع الحفاظ على query string وأسماء الملفات المشفرة دون تشفيرها مرتين.
- نجحت 16 حالة اختبار للواجهة، تشمل الصور ومسار proxy والتنقل في الإدارة وMeta، و13 حالة للباك إند، تشمل نقل الكاش واستبدال الصور والمعارض القديمة. نجح TypeScript وبناء الإنتاج وESLint دون أخطاء للملفات المعدلة. البناء سجّل تعذر الاتصال بالباك إند المحلي لبعض البيانات، لكنه اكتمل بنجاح.
- أداة إعادة الفحص: `node scripts/audit-product-images.mjs --mode=display --report=image-audit.json` من مجلد الواجهة. الخيارات `catalog` و`admin` و`sources` تفحص المسارات السابقة؛ وضع `display` ينفذ دالة العرض الفعلية المعدلة. النتائج السابقة فحص لروابط الصور على الخادم المنشور قبل نشر كود الواجهة والباك إند الجديد؛ لا تمثل تأكيدًا لاستقبال الصور داخل حساب Meta أو اكتمال النشر.

## تعذر تنزيل رابط الكتالوج في Commerce Manager — 23 أكتوبر 2026

- الصورة تستخدم `https://the-vitahub.com/facebook-catalog.xml`. الفحص المباشر للرابط المنشور أعاد HTTP 404 وصفحة HTML، بينما `https://the-vitahub.com/facebook-feed.xml` أعاد HTTP 200 و`application/xml; charset=utf-8`. اختلاف اسم المسار هو السبب المباشر المثبت لفشل تنزيل الرابط الظاهر في الصورة.
- تم تحليل XML المنشور: يحتوي على 221 منتجًا و221 معرّفًا مختلفًا. طلب الملف بوكيل المستخدم `facebookexternalhit/1.1` نجح؛ صورة أول منتج أعادت HTTP 200، وتم فكها بواسطة sharp كصورة JPEG بقياس 600×600. هذا فحص لعينة واحدة من الصور، وليس لكل الصور أو لاستقبال Meta للملف.
- أُضيف rewrite داخلي من `/facebook-catalog.xml` إلى `/facebook-feed.xml` لاستخدام معالج XML الموجود نفسه، مع إضافة الرابط إلى قواعد رؤوس الوصول العامة و`robots.ts`.
- نجح اختبار إعدادات التوجيه بأداة Next.js `unstable_getResponseFromNextConfig` للرابط مع query string وبدونها، بما يشمل الوجهة ورؤوس الوصول وعدم إرسال redirect. نجحت اختبارات Meta الخمسة وESLint للملفين المعدلين، واكتمل بناء الإنتاج وفحص TypeScript. ظهرت رسائل تعذر اتصال الباك إند المحلي أثناء توليد بعض الصفحات، لكنها لم تمنع نجاح البناء.
- لم يُشغّل اختبار HTTP لنسخة الإنتاج المحلية: رفضت المراجعة الآلية أمر تشغيل الخادم برسالة `blocked by policy`. اختبار إعدادات التوجيه لا يثبت استجابة خادم HTTP فعلي بعد النشر.
- لم يُنشر التعديل ولم يتم تعديل حساب Meta. يمكن استخدام رابط `/facebook-feed.xml` المنشور حاليًا مباشرةً في Commerce Manager؛ دعم `/facebook-catalog.xml` يحتاج نشر نسخة الواجهة المعدلة. قبول المصدر والاستيراد داخل Meta لم يُختبرا من الحساب.

## صور الكتالوج — 19 أكتوبر 2026

- فحص المصدر المنشور `https://the-vitahub.com/facebook-feed.xml` أظهر 221 رابط صورة. جميع الروابط أعادت HTTP 200 وملفات JPEG قابلة للفك باستخدام sharp عند الفحص بوكيل مستخدم `facebookexternalhit`؛ رابط واحد احتاج إعادة المحاولة بعد انتهاء المهلة. هذا يثبت إمكانية تنزيل الصور من جهة الفحص، ولا يثبت استقبال Meta لها.
- ملف `https://the-vitahub.com/robots.txt` المنشور كان مطابقًا للملف القديم في `public/robots.txt`: يحظر `/api/*`، ويستثني `/api/images/` فقط، بينما روابط صور الكتالوج تستخدم `/api/catalog/image/`. هذا حظر فعلي للمسار في قواعد الزحف، وسبب محتمل لغياب الصور؛ لم يُفحص سجل الاستيراد داخل حساب Meta.
- أُزيل `public/robots.txt` حتى يكون `src/app/robots.ts` المصدر الوحيد. قواعده الموجودة تسمح بـ `/api/catalog/` والصور المرفوعة وملفات التغذية.
- نجح بناء الإنتاج وفحص TypeScript واختبارات Meta الخمسة. اختبار HTTP لنسخة الإنتاج المحلية أعاد قواعد تسمح بالصورة الرئيسية وصور المعرض وملفات التغذية، مع استمرار حظر `/api/orders` و`/admin` و`/checkout` و`/profile`. البناء أظهر تحذيرات تعذر الاتصال بالباك إند المحلي لبعض الصفحات، لكنه اكتمل.
- يلزم نشر الواجهة أولًا، ثم التأكد من وجود `Allow: /api/catalog/` في `robots.txt` المنشور. بعد ذلك أعد استيراد مصدر البيانات الموجود داخل Commerce Manager وافحص صورة منتج وسجل أخطاء الاستيراد. لم يُنشر هذا التعديل ولم يُعد استيراد الكتالوج أثناء الفحص.

## ما ثبت بالفحص

- الصور المرفقة تعرض مطابقة 0% وتنبيهات لعدم استقبال أحداث ViewContent وAddToCart خلال آخر 7 أيام. هذه بيانات تاريخية، وليست نتيجة اختبار الحساب بعد التعديل.
- الموقع وملف XML المنشوران فُحصا بتاريخ 2 أكتوبر 2026. الملف يحتوي على 221 معرّف منتج مختلفًا. معرّف عينة من API المنتجات يطابق معرّفها في الملف.
- الكود الحالي يرسل product.id تلقائيًا لكل منتج. لا يوجد معرّف منتج ثابت لكل الموقع. ملفا XML وCSV يستخدمان المعرّف نفسه.
- سياسة CSP المنشورة كانت تسمح بتحميل مكتبة connect.facebook.net، لكنها لا تسمح باتصالات fetch/beacon إلى https://www.facebook.com. السماح بصور Facebook وحده لا يكفي للسماح بهذه الاتصالات. تم إضافة هذا المصدر المحدد إلى connect-src.
- تم إصلاح استعادة الأحداث المنتظرة عند تهيئة fbq متأخرًا، حتى بعد انتهاء مؤقت الانتظار.
- حدث Purchase أصبح يستخدم الطلب الذي يرجعه السيرفر بعد التحقق من المنتجات والأسعار والكميات، بدلًا من نسخة السلة المحلية.
- /api/pixel-events يحفظ إحصائيات داخلية فقط. لا يوجد إرسال إلى Conversions API في هذا المسار، ولذلك سجلات لوحة الإدارة ليست دليلًا على وصول الأحداث إلى Meta.

## التحقق بعد نشر نسخة الواجهة

1. أعد بناء الواجهة ونشرها؛ تعديل next.config.mjs لا يغير إعدادات النسخة المنشورة تلقائيًا. تحقق من أن connect-src في استجابة الموقع يحتوي على https://www.facebook.com.
2. افتح Events Manager ثم Test Events لمجموعة البيانات The Vita Hub Pixel، بالمعرّف 2785073648526058، أو المعرّف المهيأ فعليًا إذا تم تغييره.
3. افتح منتجين مختلفين، ثم أضف كليهما للسلة. تأكد من وصول ViewContent وAddToCart، وأن content_ids تتغير مع كل منتج، وتطابق حقل Content ID/معرّف المحتوى في الكتالوج. تأكد أيضًا من content_type = product والعملة EGP والسعر والكمية الصحيحين.
4. افتح صفحة إتمام الطلب وتحقق من InitiateCheckout بكل معرّفات السلة. اختبر Purchase بطلب تجريبي متفق عليه، وتحقق أنه يصل بعد نجاح إنشاء الطلب فقط، ويشمل كل منتجات الطلب وقيمته المحفوظة. لم يُنشأ طلب حقيقي أثناء هذا الفحص.
5. في Commerce Manager تأكد أن الكتالوج المقصود مرتبط بمجموعة البيانات نفسها، وأن مصدر المنتجات هو https://the-vitahub.com/facebook-feed.xml أو ملف CSV المكافئ. قارن منتجًا فعليًا داخل حساب Meta مع نظيره في المصدر؛ توفر الملف على الموقع لا يثبت أنه المصدر المستخدم في الحساب.
6. إذا كانت معرّفات المنتجات الموجودة في Meta تختلف عن المصدر، صحح مصدر البيانات أو ربط المعرّفات بناءً على مقارنة فعلية. لا تثبت معرّف منتج واحد لكل الموقع، ولا تحذف المنتجات أو تعيد إنشاء الكتالوج اعتمادًا على الصور وحدها. الصورة التي تمنع تعديل معرّف منتج موجود لا تعني ضرورة تغيير ذلك المعرّف إذا كان مطابقًا بالفعل.
7. راجع Network في المتصفح للطلبات إلى facebook.com/tr وConsole لأخطاء CSP. اختبر في متصفح يسمح بتشغيل الـPixel، مع مراعاة اختيار ملفات الارتباط. ظهور طلب في Network لا يغني عن تأكيد استقبال الحدث في Test Events.
8. بعد استقبال الأحداث الصحيحة، راقب تشخيصات الكتالوج للفترة الجديدة. لا يُتوقع أن تختفي بيانات آخر 28 يومًا فور النشر، ولا يمكن ضمان نسبة مطابقة من اختبار محلي.

## التحقق المحلي

نتيجة التنفيذ: نجحت الاختبارات الخمسة وفحص TypeScript وبناء الإنتاج. ظهر أثناء البناء تعذر جلب بعض بيانات الصفحات من الباك إند المحلي غير المتاح، لكن البناء اكتمل بنجاح. ملف الاختبار وإعداد Next اجتازا ESLint؛ فحص الملفات المعدلة أظهر خطأين سابقين في checkout/page.tsx من قواعد react-hooks/set-state-in-effect وreact-hooks/purity، وتم التأكد أنهما موجودان أيضًا في نسخة Git السابقة.

شغّل `npm run test:meta` من مجلد الواجهة. الاختبارات تتحقق من اختلاف معرّفات المنتجات، تفاصيل الكميات والقيم، معرّف حدث الشراء، استعادة الأحداث المتأخرة، والسماح باتصال Meta في CSP.

في بيئة تمنع إنشاء عمليات اختبار فرعية يمكن تشغيل `node --test --test-isolation=none tests/meta-tracking.test.mjs` إذا كانت نسخة Node تدعم الخيار.

لم يتم الدخول إلى حساب Meta أو تغيير الكتالوج أو نشر التعديل. ملفات التسجيل الصوتي لم تُفرغ؛ الاستنتاجات مبنية على الصور والنص والكود والفحص المباشر للموقع.
