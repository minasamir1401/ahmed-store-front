# التحقق من إصلاح Meta Pixel والكتالوج

## ما ثبت بالفحص

- الصور المرفقة تعرض مطابقة 0% وتنبيهات لعدم استقبال أحداث ViewContent وAddToCart خلال آخر 7 أيام. هذه بيانات تاريخية، وليست نتيجة اختبار الحساب بعد التعديل.
- الموقع وملف XML المنشوران فُحصا بتاريخ 2 أكتوبر 2026. الملف يحتوي على 221 معرّف منتج مختلفًا. معرّف عينة من API المنتجات يطابق معرّفها في الملف.
- الكود الحالي يرسل product.id تلقائيًا لكل منتج. لا يوجد معرّف منتج ثابت لكل الموقع. ملفا XML وCSV يستخدمان المعرّف نفسه.
- سياسة CSP المنشورة كانت تسمح بتحميل مكتبة connect.facebook.net، لكنها لا تسمح باتصالات fetch/beacon إلى https://www.facebook.com. السماح بصور Facebook وحده لا يكفي للسماح بهذه الاتصالات. تم إضافة هذا المصدر المحدد إلى connect-src.
- تم إصلاح استعادة الأحداث المنتظرة عند تهيئة fbq متأخرًا، حتى بعد انتهاء مؤقت الانتظار.
- حدث Purchase أصبح يستخدم الطلب الذي يرجعه السيرفر بعد التحقق من المنتجات والأسعار والكميات، بدلًا من نسخة السلة المحلية.
- /api/pixel-events يحفظ إحصائيات داخلية فقط. لا يوجد إرسال إلى Conversions API في هذا المسار، ولذلك سجلات لوحة الإدارة ليست دليلًا على وصول الأحداث إلى Meta.

## التحقق بعد نشر نسخة الواجهة

1. أعد بناء الواجهة ونشرها؛ تعديل next.config.mjs لا يغير إعدادات النسخة المنشورة تلقائيًا. تحقق من أن connect-src في استجابة الموقع يحتوي على https://www.facebook.com.
2. افتح Events Manager ثم Test Events لمجموعة البيانات The Vita Hub Pixel، بالمعرّف 2785073648526058، أو المعرّف المهيأ فعليًا إذا تم تغييره.
3. افتح منتجين مختلفين، ثم أضف كليهما للسلة. تأكد من وصول ViewContent وAddToCart، وأن content_ids تتغير مع كل منتج، وتطابق حقل Content ID/معرّف المحتوى في الكتالوج. تأكد أيضًا من content_type = product والعملة EGP والسعر والكمية الصحيحين.
4. افتح صفحة إتمام الطلب وتحقق من InitiateCheckout بكل معرّفات السلة. اختبر Purchase بطلب تجريبي متفق عليه، وتحقق أنه يصل بعد نجاح إنشاء الطلب فقط، ويشمل كل منتجات الطلب وقيمته المحفوظة. لم يُنشأ طلب حقيقي أثناء هذا الفحص.
5. في Commerce Manager تأكد أن الكتالوج المقصود مرتبط بمجموعة البيانات نفسها، وأن مصدر المنتجات هو https://the-vitahub.com/facebook-feed.xml أو ملف CSV المكافئ. قارن منتجًا فعليًا داخل حساب Meta مع نظيره في المصدر؛ توفر الملف على الموقع لا يثبت أنه المصدر المستخدم في الحساب.
6. إذا كانت معرّفات المنتجات الموجودة في Meta تختلف عن المصدر، صحح مصدر البيانات أو ربط المعرّفات بناءً على مقارنة فعلية. لا تثبت معرّف منتج واحد لكل الموقع، ولا تحذف المنتجات أو تعيد إنشاء الكتالوج اعتمادًا على الصور وحدها. الصورة التي تمنع تعديل معرّف منتج موجود لا تعني ضرورة تغيير ذلك المعرّف إذا كان مطابقًا بالفعل.
7. راجع Network في المتصفح للطلبات إلى facebook.com/tr وConsole لأخطاء CSP. اختبر في متصفح يسمح بتشغيل الـPixel، مع مراعاة اختيار ملفات الارتباط. ظهور طلب في Network لا يغني عن تأكيد استقبال الحدث في Test Events.
8. بعد استقبال الأحداث الصحيحة، راقب تشخيصات الكتالوج للفترة الجديدة. لا يُتوقع أن تختفي بيانات آخر 28 يومًا فور النشر، ولا يمكن ضمان نسبة مطابقة من اختبار محلي.

## التحقق المحلي

نتيجة التنفيذ: نجحت الاختبارات الخمسة وفحص TypeScript وبناء الإنتاج. ظهر أثناء البناء تعذر جلب بعض بيانات الصفحات من الباك إند المحلي غير المتاح، لكن البناء اكتمل بنجاح. ملف الاختبار وإعداد Next اجتازا ESLint؛ فحص الملفات المعدلة أظهر خطأين سابقين في checkout/page.tsx من قواعد react-hooks/set-state-in-effect وreact-hooks/purity، وتم التأكد أنهما موجودان أيضًا في نسخة Git السابقة.

شغّل `npm run test:meta` من مجلد الواجهة. الاختبارات تتحقق من اختلاف معرّفات المنتجات، تفاصيل الكميات والقيم، معرّف حدث الشراء، استعادة الأحداث المتأخرة، والسماح باتصال Meta في CSP.

في بيئة تمنع إنشاء عمليات اختبار فرعية يمكن تشغيل `node --test --test-isolation=none tests/meta-tracking.test.mjs` إذا كانت نسخة Node تدعم الخيار.

لم يتم الدخول إلى حساب Meta أو تغيير الكتالوج أو نشر التعديل. ملفات التسجيل الصوتي لم تُفرغ؛ الاستنتاجات مبنية على الصور والنص والكود والفحص المباشر للموقع.
